# DESIGN v2.3: Mesh-to-Mesh Federation

**Status: PLAN — nothing here is implemented.** Plan-only PR; implementation starts only on the owner's explicit approval, then as separate PRs (§11). **Supersedes `DESIGN_FEDERATION.md`** (single-bus multi-tenant, scrapped by the owner the day it merged: *"why else would we do this if it's all on one bus?"*). v2.3 folds three evaluator rounds (NO-GO, NO-GO-narrow, then GO-with-amendments — ten pins, all folded in §16): every mechanism below was checked against main `74771ee` (and the in-lane #89/#90/#95 branches where named), and every point a builder would otherwise have had to decide is decided here (§14 ledger, §15 round-2 resolutions).

**The shape, in one paragraph:** every organisation runs **its own claude-mesh instance with its own admin token**. Meshes **peer directly and pairwise** — no hub, no shared bus, no shared registry. A mesh joins a peering by **presenting a key the other mesh's admin minted**; after that, agents on one mesh address agents on the other as `<alias>:<agent>`. **Each admin controls what crosses their own border and which message types** — the sender decides what may leave, the receiver decides what may enter, and neither trusts the other's check. Your mesh stays yours.

## 1. The trust join — read first

Between buses the hard question is: **what does mesh A accept from mesh B, and on whose authority?** The known failure is each side assuming the other validated. Every check below has one owner, runs on the side that suffers if it is wrong, and fails closed. Nothing is delegated across the border except the one thing that must be (row 7), which is stated.

| # | Check | Owner | Consults | On failure |
|---|---|---|---|---|
| 1 | May mesh B connect to my border? | Receiver A | A's `peers` row for the alias: token, not disabled, protocol compatible | socket closed `AUTH_FAILED` `unknown agent` — the ONE refusal every peer-reachable auth failure gets (C9; #104) |
| 2 | May local agent X send to `alias:y`? | Sender B | `outbound_peers` row enabled + outbound ACL edge `X → alias:y` + kind ∈ outbound kinds | `AGENT_NOT_FOUND`, byte-identical to a nonexistent local id |
| 3 | May `alias:x` reach local agent Y? | Receiver A | inbound ACL edge `alias:x → Y`, kind ∈ inbound kinds, Y exists | one uniform `RELAY_REFUSED` to the peer — the peer learns a relay was refused, never *why* (no existence or ACL oracle to a peer either) |
| 4 | Is this one hop? | Receiver A | relay `from` and `to` are bare (no `:`) | `RELAY_REFUSED` |
| 5 | Is the peer within its rate? | Receiver A | token bucket per alias, counted on **every** relay frame incl. refused ones, checked first after row 1 | `RATE_LIMITED` (the peer is told — it needs to back off) |
| 6 | Has this relay been seen before? | Receiver A | `relays(alias, remote_msg_id)` | duplicate → re-`ack`, deliver nothing (idempotent) |
| 7 | Is `from` really agent X on mesh B? | **Sender B** (the authenticated agent socket's own id) | — | **Receiver A trusts B's admin for every name under `alias:` — this is the single cross-border delegation, and it is a delegation to an admin, not to an agent** |
| 8 | May anyone write an ACL edge naming `alias:z`? | The bus holding the edge | the peering in the implied direction exists | `aclGrant` refuses, whoever writes it (§5.4) |

**1.1 Where an agent id flows today, and what a remote id does there.** A remote id is a third inhabitant of a `TEXT` column; no type forces the audit (#84's `{mode:'unauthenticated'}` did and found a second fall-through), so the plan enumerates:

| Consumer | With `alias:x` | Owner |
|---|---|---|
| `getAgentById` in `routeDirect` | not reached for a real remote: the `:` branch (§5.3) runs first; it FALLS THROUGH to this lookup only when the prefix is not an enabled outbound alias — which preserves any legacy local id containing `:` and keeps `AGENT_NOT_FOUND` uniform | sender |
| `getAgentById` on the relay path | never called with a remote id (row 4 runs first) | receiver |
| A local reply to `from = alias:x` | an ordinary outbound send → row 2 (named because it is where this will be forgotten) | sender |
| `aclCheck` / `aclGrant` | after the F0 `acl` rebuild (no FKs), remote ids are ordinary endpoints; the gate is at write time | the holding bus |
| `broadcastStatus` / `list_presence` | never render or target a remote id: peer sockets have `agentId: null` and are skipped by every `state.agentId !== null` guard by construction; no presence crosses a border | receiver |
| `GET /messages` node-scoping | a local agent's own history legitimately contains remote `from`/`to` rows | — |
| File ownership predicates | unreachable: peer sockets cannot send file frames; files never cross | receiver |
| Metrics | labels per **peer alias** and direction, never per remote agent (#12) | both |
| MCP `mesh_send` / `mesh_broadcast` | `as_agent` containing `:` is refused (a local plane must not forge a remote sender); a remote `to` flows into `routeDirect`'s branch | sender |
| MCP `mesh_discover` / `mesh_status` | local roster only, unchanged | — |
| Observer tap | local observers see relayed inbound rows and outbound remote-addressed rows as stored (stated policy) | each bus, its own half |
| Reminders / topics / subscriptions | self-only / local-only; a peer socket cannot `remind`, `subscribe`, `publish`; FKs on those tables stay | receiver |
| Logs / error strings | may contain remote ids (not secrets); never `outbound_peers.token` (C7) | — |

## 2. Constraints

- **C1** One admin per mesh; peers never hold each other's admin token; a peer key grants registration only.
- **C2** Naming must not grant: addressing an alias or remote agent grants nothing until this mesh's admin registered the peering in that direction and wrote the edge. Unknown = refused, never created.
- **C3** Pure-bus: cross-bus routing is bus work; analytics stay outside.
- **C4** Remote ids compose over the existing per-pair `acl` as ordinary endpoints — **which requires removing the `acl` table's foreign keys to `agents` (§4, F0)**; the peering is an outer gate at write time, never a replacement for the pair edge.
- **C5** No behaviour change for any id or frame in use today until a peer key is minted; the two additive refusals that DO change with zero peers are named here (a new local id containing `:` → 400; a `relay` frame from an agent socket → `NOT_ALLOWED` instead of today's `NOT_IMPLEMENTED`) — neither affects any fleet id or test. Existing suite green with **exactly two modified tests, named in advance**: `db.test.ts` ~860-875 assert that an `acl` row naming a nonexistent agent throws a FOREIGN KEY violation — after the F0 rebuild that refusal moves from the DB to `aclGrant` (which gains an existence check for bare ids, §5.4), so those two tests assert the same property via the new mechanism. Everything else unmodified. **Legacy agent ids containing `:` keep working** (§5.3 fall-through, with the prefix-collision rule in §3) and are logged at boot.
- **C6** Directional independence: A→B and B→A are separate registrations, sockets, ACL, and revocations. "Peered" is never a single fact; every API names the direction.
- **C7** The DB will hold exactly one class of live credential: `outbound_peers.token` (the sender must present it; everything else is hashed). It is never returned by any read API, never logged, never a metric label; the F2 migration is flagged in its PR as **changing the DB's sensitivity class** so backups/exports/dumps are told, not surprised.
- **C8** A peer must not be able to crash the receiver: **#94 (PR #95: frame-dispatcher guard + `DUPLICATE_MSG_ID` on `send`) is a prerequisite of F1, and the guard is colour-blind** — it catches a synchronous throw AND a rejected promise regardless of whether the handler is `async` (try/catch the call; a thenable return routes rejections to the same report path), pinned by a test whose handler returns a rejected promise. Today's WS message handler is synchronous; F1 adds awaitable work to the relay path, and a sync-only guard would lapse on a one-word `async` edit (the HTTP plane's #68 comment records exactly that incident). Severity of the unguarded case: measured, not inferred — see the PR #93 body.
- **C9 — UNIFORM REFUSAL.** **Distinct failure causes OF THE SAME QUESTION must produce indistinguishable outcomes to an unauthenticated (or not-yet-trusted) caller: a refusal must not teach the caller anything it could not already determine.** "The same question": nonexistent alias / wrong token / revoked peer all answer "may I authenticate?" and must be one refusal. A refusal to a DIFFERENT question is not an instance: `ws-server.ts:782` `NOT_ALLOWED` ("peer sockets may send relay or ping only") answers "may this socket send this frame type?" and is distinguishable from the relay path's `RELAY_REFUSED` by design — named here because it is the case a new reader meets first. Credential-first ordering is one IMPLEMENTATION of this, not the rule — reordering checks while still emitting two different messages does not comply. Instances on main (a409141, verified 2026-09-05): `server/ws-server.ts` peer auth folds `disabled` into the same refusal as a wrong token (`unknown agent` for a nonexistent alias, a wrong token, and a revoked peer alike — the #104 finding), validates `protocol` only after the peer credential matched (a prober cannot learn which version this mesh speaks), and `POST /peers/register` returns one constant 403 body for every reason with the reason going only to the log. Why it is written down: its violation is UNDETECTABLE by testing an endpoint's happy path or any single refusal — it is detectable only by comparing the refusals a caller can reach AS A SET, byte for byte, which is how every instance above was found (each arrived as a review finding, not as design). Every instance looks like an inefficiency to a reader who does not know the rule, and a tidy-up that hoists a cheap check above the credential check, or gives one cause its own helpful message, is the regression — so each site carries a one-line comment "ordered/folded per C9" naming this constraint as the authority, and every new door (F2's `/outbound-peers`, the remote branch of `routeDirect`) is built to it. **Two coupled obligations, both mandatory at every C9 site.** (i) THE SET TEST — the detection method this constraint names is the one it requires: drive every reachable refusal cause of the same question at that door and assert the response bytes are identical (status, headers, body); a door can pass every per-guard test and still violate C9 when someone adds a `message` to one branch, and only putting the refusals side by side sees it. This set test is RE-RUN after ANY change that touches a refusal at that door, not only when it is first written: a fix's scope is bounded by the instrument that found the defect, and the set test is the wider instrument — it only helps if it runs after remediation, not merely at it (#119). (ii) THE PER-GUARD TEST — the same property that makes the refusal secure makes a mutant undetectable: a green suite at a C9 site cannot tell which guard refused, BY DESIGN, so a test of any single guard there must make every OTHER check pass on purpose (enumerated in the test), and the mutant dropping the guard must ADMIT the input (deliver, write, authenticate) — never merely be refused by a neighbour. A convention that creates obligations ships them, and a constraint that justifies itself by naming a detection method has committed to requiring that method. **Scope:** C9 binds doors reached by callers OUTSIDE the trust boundary — peer auth, `/peers/register`, the relay path, and any refusal a LOCAL agent receives about a REMOTE mesh (the remote branch of `routeDirect`). It does NOT bind admin-authenticated doors: an admin can already enumerate agents, peers and keys, so distinguishable refusals there teach nothing (C9's own test) and their diagnostic value is real — making them uniform would be the #107 error of applying uniformity to the system instead of the prober-reachable surface. A refusal that reveals only the caller's OWN local configuration (`KIND_NOT_ALLOWED` on the remote branch — the sender's outbound kinds, crossing no border) is consistent with C9 and is marked as such where it occurs. Every door states in its PR body which side of the boundary it is on and why, because "we applied C9 everywhere" and "we decided C9 does not apply here, because" look identical in a diff and only one is a decision. (#111)

## 3. Concepts

- **Peer alias** — the name *this* mesh gives a remote mesh. Local to the assigning mesh; no global namespace. Grammar `^[a-z0-9][a-z0-9-]{0,62}$`; `mesh` reserved; an alias may not equal any existing local agent id, and `POST /agents` refuses an id equal to an existing alias. **Outbound aliases additionally may not be the `:`-prefix of any existing local id** (`POST /outbound-peers {alias:'foo'}` is refused while a legacy local agent `foo:bar` exists, and `POST /agents` refuses a new id whose prefix before `:` is an outbound alias) — otherwise §5.3's branch would shadow the legacy id.
- **Remote id** — `<alias>:<agent>`. Local ids minted from F0 on may not contain `:`; legacy ones are tolerated (C5).
- **Peer key** — minted by the receiver's admin for an alias; shown once; hashed; expiry; revocable; at most one live (non-revoked) key per alias (`409` otherwise).
- **Peering (directional)** — receiver side: a `peers` row; sender side: an `outbound_peers` row holding the receiver's URL, the token the receiver issued, and **`assigned_alias`** — the name the receiver gave us, which the forwarder presents at auth.
- **Relay** — the only message frame a peer socket may send; carries the sender's local agent id and the receiver-local target.

## 4. Data model (each mesh; additive except the `acl` rebuild)

```sql
-- F0: rebuild acl WITHOUT the REFERENCES agents(id) ON DELETE CASCADE constraints (SQLite cannot drop an FK in place):
--   The base CREATE TABLE acl DDL ALSO changes to the FK-less form (fresh DBs never rebuild); the probe rebuild is for upgraded DBs only. The PRAGMA is set OUTSIDE any
--   db.transaction() (foreign_keys=OFF is a no-op inside one — verified; the function throws if called inside one), then the DDL AND the index replay run INSIDE one explicit transaction so a crash mid-rebuild rolls back (as built in #97, crash-injection tested); idempotent via the probe: rebuild only if PRAGMA foreign_key_list(acl) is non-empty. Steps: foreign_keys=OFF; CREATE TABLE acl_new(... no FKs ...); INSERT ... SELECT; DROP acl; RENAME; recreate every acl index
--   present at that time, enumerated as `SELECT sql FROM sqlite_master WHERE type='index' AND tbl_name='acl' AND sql IS NOT NULL` captured BEFORE the DROP and re-exec'd
--   after the RENAME (the PK autoindex has NULL sql and is skipped; idx_acl_reverse lands with #89, which precedes F0); foreign_keys=ON. deleteAgent() then deletes the agent's acl rows EXPLICITLY (it relied on
--   the cascade). F0 ADDS migration-chain cases (NEW, not 'covered'): snapshots WITH acl rows survive the rebuild edge-for-edge; deleteAgent still clears them.
CREATE TABLE peer_keys (id TEXT PRIMARY KEY, key_hash TEXT NOT NULL, alias TEXT NOT NULL, kinds TEXT NOT NULL DEFAULT '["direct"]',
  rate_per_min INTEGER NOT NULL DEFAULT 600, expires_at INTEGER, revoked_at INTEGER, note TEXT, created_at INTEGER NOT NULL);
CREATE TABLE peers (alias TEXT PRIMARY KEY, token_hash TEXT NOT NULL, key_id TEXT NOT NULL, kinds TEXT NOT NULL, rate_per_min INTEGER NOT NULL,
  disabled INTEGER NOT NULL DEFAULT 0, registered_at INTEGER NOT NULL, last_alive INTEGER);           -- protocol version lives in the handshake only (D7); a peer TOKEN has no expiry of its own — key expiry gates registration only, revocation is the kill (D10)
CREATE TABLE outbound_peers (alias TEXT PRIMARY KEY, url TEXT NOT NULL, token TEXT NOT NULL /* C7 */, assigned_alias TEXT NOT NULL,
  kinds TEXT NOT NULL, rate_per_min INTEGER NOT NULL DEFAULT 600, enabled INTEGER NOT NULL DEFAULT 1, created_at INTEGER NOT NULL, last_alive INTEGER);
CREATE TABLE relays (alias TEXT NOT NULL, remote_msg_id TEXT NOT NULL, local_msg_id TEXT NOT NULL, seen_at INTEGER NOT NULL, PRIMARY KEY(alias, remote_msg_id));  -- dedupe; swept after RELAY_DEDUPE_MS = 7 days as a step of the cleanup tick (housekeeping); the forwarder never re-sends a row older than the same window (§5.3), so the two bounds agree
ALTER TABLE messages ADD COLUMN failed_code TEXT;   -- set when the remote refused; row keeps history
```

## 5. Enforcement and wire

**5.1 Border listener (receiver).** In the WS auth handler, after the frame's `agent_id`/`token` are validated as strings and **before** `getAgentById`: look up `peers` by `alias = agent_id` and compare the token hash with the timing-safe compare (the WS style: id-keyed then compare — not #75's token-hash scan). If a `peers` row matches: (a) if `disabled` → `AUTH_FAILED` `unknown agent` — the ONE refusal, see the uniform-refusal note below (C9; #104); (b) **then** check `protocol` — absent or unsupported → `PROTOCOL_MISMATCH`, logged with both versions, socket closed; (c) `ConnState` gets `agentId: null, peerAlias: alias`, **and the peer branch `return`s before the agent post-auth block** — that block (`setOnline`, `agentIndex.set`, the pending-queue count, `drainQueue`/`drainFileQueue`, `broadcastStatus`, observer registration) is NOT guarded by `state.agentId` today (it uses the local `agentId` variable), so skipping it is an explicit early return, not a property of the null. The close path likewise branches on `peerAlias` first: it deletes from `peerIndex` **only if `peerIndex.get(alias) === ws`** (a late close from a replaced socket must not evict the live one — the #92 shape), and touches neither `agentIndex` nor `setOnline`. `handlePing` for a peer stamps `peers.last_alive` and returns. **Second socket for the same alias: newer wins** — the older is closed with `PEER_REPLACED` before `peerIndex.set` (D11). A peer auth failure of any kind (unknown alias, bad token, disabled) is ONE refusal — `AUTH_FAILED` with message `unknown agent`, the message a stranger already sees, chosen so that neither revocation state nor alias existence leaks (C9). The original text here prescribed the invalid-token message; #104 measured that as a revocation oracle and fixed it — do NOT reintroduce it. the agent path's own refusals were folded to the same frame by #117 (issue #116); on any tree older than #117 a bad AGENT token said `invalid token`, so do not assert cross-door identity there; (d) the socket is put in a new `peerIndex: Map<alias, WebSocket>` exposed on `WsServerHandle`; (e) `auth_ok` for a peer is `{type:'auth_ok', peer: alias, protocol: 1}` (no queue fields). If no `peers` row matches, auth proceeds exactly as today; the `protocol` field is ignored for agents (C5). Peer-socket frame allowlist: **`relay` and `ping`** (the SDK's heartbeat must be answered or the forwarder tears down every 60 s); `ping` from a peer stamps `peers.last_alive`; everything else → `NOT_ALLOWED`; `relay` from an agent socket → `NOT_ALLOWED`. A peer that becomes disabled is closed immediately by revocation **and** by a sweep that lives in `startCleanup` as its own interval (`PEER_SWEEP_INTERVAL_MS = 15_000`, own `setInterval` + own `try`, a function-parameter test seam, `startCleanup` gaining a `peerIndex` parameter — the #84 `DISABLED_SWEEP` shape verbatim, at peer granularity).

**5.2 Relay frame.** `{type:'relay', msg_id, from, to, kind:'direct', payload, content_type?, ttl_ms?}` — `msg_id` is the **sender's local row id** (unique on the sender). Receiver, in order, each fail-closed: peer not disabled (auth already guaranteed; re-checked cheaply) → **rate bucket** (per alias, `rate_per_min` sustained, burst = the same number, in memory, counts every relay) → `from`/`to` bare (row 4) → `kind ∈ peers.kinds` → dedupe: if `(alias, msg_id) ∈ relays` → re-`ack`, stop → `to` exists → inbound `aclCheck(alias+':'+from, to)` → **mint a local row id**, insert `relays(alias, msg_id, local_id)`, then deliver/queue with `from_agent = alias:from` via **`deliverOrQueue(db, agentIndex, msg)` — a helper extracted from `routeDirect`'s existing insert/deliver/queue block, used by both paths unchanged** (the relay handler is its own function; it does NOT call `routeDirect`, whose check order and error codes differ), then the relay handler calls `emitTap` itself with `from = alias:from` (the tap call sits outside the extracted block in `routeDirect`; §1.1's policy requires it here) → `ack {ref: msg_id}`. Frame validation before any check: `msg_id`, `from`, `to`, `payload` are non-empty strings; `from`/`to` are ≤ 256 bytes and contain no `:` (the one-hop rule IS this check — there is no other agent-id grammar on the bus); `kind === 'direct'`; size ≤ the existing 1 MB cap. Every attributable refusal — `RELAY_REFUSED` AND `RATE_LIMITED` — carries `ref: msg_id` whenever `msg_id` is a string (the SDK settles the `relay()` waiter only on a `ref`; without it the forwarder would wait out `ACK_TIMEOUT` and D12's transient branch would be unreachable); only a frame without a string `msg_id` gets no `ref` (mirrors #95's `INTERNAL` convention). Receiver `ttl_ms` mapping is exactly `routeDirect`'s: absent → the 300 000 default, `0` → ephemeral, else `now + ttl_ms`. Refusals: `RATE_LIMITED` (told), everything from row 3/4 → uniform `RELAY_REFUSED {ref: msg_id}`. Any handler throw is caught by #94's dispatcher guard.

**5.3 Outbound (sender).** In `routeDirect`, before the existing recipient lookup: if `frame.to` contains `:`, split at the FIRST `:`; if the prefix is an **enabled `outbound_peers` alias** → remote path; else → fall through to the local lookup unchanged (legacy ids with `:` keep working; an unknown alias yields the same `AGENT_NOT_FOUND` as an unknown local id). Remote path: the remainder must itself be bare (a second `:` → `AGENT_NOT_FOUND`, never a wasted relay) → `kind ∈ outbound kinds` (else `KIND_NOT_ALLOWED` — the sender's own configuration, no cross-border oracle) → outbound `aclCheck(from_agent, frame.to)` (fail → `AGENT_NOT_FOUND`) → #95's duplicate check (`getMessage(db, frame.msg_id) !== null → DUPLICATE_MSG_ID`, same code, same position: **before any side effect — and the first side effect is the accepted-and-routed metrics (`incSent`/`observePayloadBytes`), not the insert, so the check must sit above the metrics, not merely above the insert**; #96's test pins exactly that) → insert the row with `to_agent = frame.to`, `expires_at` from `ttl_ms` as today, **except `ttl_ms = 0` (ephemeral): relay immediately if the peering socket is currently connected, else drop with `ack` — 'online' for a remote id means 'peering connected'** → **ack the local sender now** (D8) → `borderEvents.emit('enqueued', alias)` (a module-level `EventEmitter` exported by `server/border.ts`; `router.ts` imports it; `border.ts` imports the SDK via `../client/src/client.ts` — the same relative path `router.ts` uses — and `db.ts`, never `router.ts`). **Invariant, named:** `routeDirect` remains SYNCHRONOUS through the duplicate check and the insert — the #95 dedupe's atomicity rests on it (two concurrent frames with the same `msg_id` must not both pass the check before either inserts); the emit is fire-and-forget AFTER the synchronous section and is never awaited inside `routeDirect`. Pinned by a two-concurrent-duplicates test whose async-before-insert mutant must fail. No `from_agent` refusal in `routeDirect` (a legacy local id containing `:` must keep sending — C5; the WS `from_agent` is the socket's own identity and cannot be forged). The forge risk is the MCP plane only: `mesh_send`/`mesh_broadcast` require `as_agent` to be an EXISTING LOCAL agent (`getAgentById !== null`, else `AGENT_NOT_FOUND`) — a remote id is never a local row, so it can never be impersonated from stdio.

**Border forwarder** (new module `server/border.ts`, in-process): one instance per enabled `outbound_peers` row, started at boot and on `POST /outbound-peers`, stopped on `DELETE`/disable. Uses `PeerClient` (§7) with `agent_id = assigned_alias`, `protocol: 1`. Drain: `SELECT … FROM messages WHERE to_agent >= ? AND to_agent < ? AND delivered_at IS NULL AND failed_code IS NULL AND (expires_at IS NULL OR expires_at >= now) AND sent_at >= now - RELAY_DEDUPE_MS ORDER BY sent_at LIMIT ?` with the bounds `alias + ':'` and `alias + ';'` (a range the `to_agent` index serves — `LIKE` was verified to full-scan), excluding an in-memory **in-flight set**; rows older than the dedupe window are expired (`expires_at = now`) rather than sent. **Pacing (sender-side, so a backlog drains UNDER the receiver's bucket instead of tripping it):** `outbound_peers.rate_per_min` (operator-supplied from the register response; default 600) feeds a sender-side token bucket per peering — sustained `rate_per_min`, burst `rate_per_min` — AND an in-flight cap of `min(50, rate_per_min / 4)`; a relay is sent only when both allow (an in-flight cap alone is a concurrency bound, not a rate — 50 in flight with fast acks would push 600+ rows in a second). A `RATE_LIMITED` from the receiver halves the local bucket's refill until the next success, so a stale or over-stated local rate still converges. Each relay carries `ttl_ms = max(1, expires_at - now)` (omitted when `expires_at IS NULL`) — never `0` for a stored row, since `0` means ephemeral on the receiver; `ttl_ms = 0` relays arise only from §5.3's immediate-ephemeral path. **Outcome taxonomy (via `PeerClient.relay()`):** resolved → `markDelivered`; rejected with **permanent** `RELAY_REFUSED` → `failed_code = code` AND `expires_at = now` (so retention and pending counts stop treating it as live) and, if the originating agent is connected (`agentIndex.get(from_agent)`), one `{type:'error', code:'REMOTE_REFUSED', ref: row.id}` — best effort (D5); rejected with **transient** `RATE_LIMITED`, `ACK_TIMEOUT`, or `CONNECTION_RESET` → the row stays pending, leaves in-flight, and the peering backs off (1 s doubling to 60 s, reset on the next success). Drain triggers: connect/reconnect, `borderEvents` for the alias, and a 30 s backstop tick. Forwarder start/stop/restart is event-driven from the `/outbound-peers` handlers, which receive the `Map<alias, Forwarder>` the way `startHttpAdmin` receives `agentIndex` today; `peerIndex` reaches http-admin the same way. No local ack is ever deferred; no `ACK_TIMEOUT` reaches an agent.

**5.4 The ACL chokepoint for remote ids.** `aclGrant` (the only `INSERT INTO acl`; callers `POST /acl` and MCP `mesh_acl_allow`) gains, after the F0 rebuild, the existence check the FK used to provide: **a bare endpoint must be an existing local agent**, refused by THROWING an `Error` with `code: 'AGENT_NOT_FOUND'` (the FK threw too, so the two named `db.test.ts` tests re-point to `expect(() => aclGrant(...)).toThrow()`); `handleAclPost` maps it to its existing 404, and `handleMeshAclAllow` catches it and returns `{error:'AGENT_NOT_FOUND'}` with `isError: true` (today a ghost id on MCP escapes as a JSON-RPC error — this is the one deliberate MCP shape change, stated). An endpoint containing `:` that is an existing local id is treated as local (legacy). Otherwise a `:` endpoint is remote and the alias must have a peering in the implied direction — `local → alias:x` needs an enabled `outbound_peers` row, `alias:x → local` needs a non-disabled `peers` row — read via new `db.ts` helpers (`hasOutboundPeer`, `hasInboundPeer`; `db.ts` never imports `http-admin`). `handleAclPost`, `handleAclDelete`, `handleAclGet?agent=` currently 404 on `getAgentById` for each endpoint; each gains a "remote id ⇒ skip existence check, apply the peering rule" branch so revoke and list work for remote ids too.

**5.5 Addressing.** Agents see remote ids as the FQ string and reply to it (row 2). Local ids stay bare. No normalization layer exists or is needed.

**5.6 Revocation.** Receiver: `DELETE /peer-keys/:id` → `peers.disabled = 1` in the same transaction; socket closed immediately via `peerIndex` and by the sweep. Sender: `DELETE /outbound-peers/:alias` → forwarder stopped **and, in the same transaction, every undelivered row to `alias:*` gets `expires_at = now`** — those rows are undeliverable by construction from that instant, and this is the only moment anyone knows it; without this, an untTL'd row (`expires_at IS NULL`, an ordinary case) would be preserved forever by `sweepRetention`'s still-deliverable exclusion, a state that predicate cannot express ("pending, and the only path is gone"). A peering socket that is merely DOWN is different and untouched: the peering may return, so its rows keep today's offline semantics. **Receiver-side revocation seen from the sender:** `PeerClient` treats `AUTH_FAILED` as fatal at ANY time (not only first auth, as `MeshClient` does) — a revoked or rotated peering does not reconnect every 30 s forever; the forwarder sets `enabled = 0` with a logged reason, and the operator re-registers or deletes it.

## 6. Admin API (each mesh; admin port; admin token unless stated)

- `POST /peer-keys {alias, kinds?, rate_per_min?, expires_at?, note?}` → `{id, key(once), alias, kinds, rate_per_min, expires_at}`; refuses an alias equal to a local agent id or `mesh`, an alias with a live key (`409`), bad grammar. `GET /peer-keys` (no hashes, live-peer state per alias). `DELETE /peer-keys/:id` (§5.6).
- `POST /peers/register` — authenticated by a peer key via `auth: 'handler'` + `{mode:'unauthenticated'}` (the #84 mechanism, cherry-picked in F0 — D9). Body `{}`. Returns `{alias, token(once), kinds, rate_per_min, protocol: 1}`. Uniform `403` body on any failure; one structured server log line with the discriminator. Presenting the key again = token rotation **and** the existing peer socket for that alias is closed (no silent takeover). **Key expiry (D10, restated here with the implementation verified 2026-09-05):** per D10, `peer_keys.expires_at` bounds the window in which the key may be used to REGISTER; it does not bound the resulting peering — a registered peer holds its own token, is never re-checked against the key, and is ended only by `revokePeerKey` (which is why `minted_by_key` exists). Verified at a409141: `minted_by_key` is read only by revoke propagation, peer auth (`ws-server.ts:595`) reads `peers.token_hash` AND `peers.disabled` — `disabled` is the mechanism that makes "revocation is the kill" true — and never consults `peer_keys`; the sweep keys on `disabled = 1`. There is no time-bounded peering; if one is wanted it is a new field on `peers` with its own sweep, not a reinterpretation of this one (#114).
- `GET /peers` — inbound peerings: alias, kinds, rate, disabled, last_alive, `connected` (from `peerIndex`).
- `POST /outbound-peers {alias, url, token, assigned_alias, kinds?, rate_per_min?}` (url must be `ws://` or `wss://`; loopback allowed) / `DELETE /outbound-peers/:alias` / `GET /outbound-peers` (alias, url, assigned_alias, kinds, rate_per_min, enabled, last_alive — **never** token, C7). `PATCH /outbound-peers/:alias {enabled?, token?, url?, rate_per_min?}` — `token` and `url` are how a receiver-side token rotation or move is applied WITHOUT `DELETE` (which would expire queued mail, §5.6); the forwarder restarts with the new credential. Start/stop/restart is event-driven from these handlers, never polled.
- `POST /acl` unchanged in shape; §5.4 applies.

A peering, end to end: A's admin mints a key for alias `B` → out of band → B's admin `POST A/peers/register` → gets `{alias:'B', token}` → B's admin `POST B/outbound-peers {alias:'A', url:A, token, assigned_alias:'B'}` → both admins write their own edges. Reverse: same steps, roles swapped.

## 7. SDK changes (F0, `@claude-mesh/client`, minor version bump)

- `AuthFrame.protocol?: number` — sent only by `PeerClient`; agents unchanged.
- `MeshClient`: `rawSend` and `sendWithAck` become `protected` (they are `private` today, so a subclass cannot reach them); a new `protected authExtras(): Record<string, unknown>` hook (default `{}`) is merged into the auth frame where it is built; a `protected isFatalError(frame): boolean` hook (default: `AUTH_FAILED && !firstAuthDone`, OR `PROTOCOL_MISMATCH` at any time), consulted where today's single fatal branch is, and the fatal branch now also `emit('error', …)` before closing so a caller can observe the code post-auth (today it settles the connect promise only, which is a no-op after first auth). `PeerClient extends MeshClient`: `authExtras()` returns `{protocol: 1}`; `relay(frame): Promise<void>` over `sendWithAck` keyed by the relay `msg_id`, rejecting with the peer's `code` (`RELAY_REFUSED`/`RATE_LIMITED`) or the SDK's (`ACK_TIMEOUT`/`CONNECTION_RESET`); overrides `isFatalError` to `AUTH_FAILED || PROTOCOL_MISMATCH` at any time, and the forwarder acts on the emitted error (sets `enabled = 0` with the code in the log). Heartbeat/half-open/reconnect unchanged. Agent auth is byte-identical (the hook adds nothing for `MeshClient`); the runtime's SDK pin is unaffected.

## 9. Worked example — PowerOUT (illustrative)

Each student org = its own mesh (one container of the tagged image). Orchestrator on the host mesh. Inter-org play = pairwise peerings the game backend sets up through each org mesh's admin API (org-red mints a key for `org-blue`, and vice versa; each writes edges only for the personas that should be reachable). Backend → orchestrator = org mesh → host mesh registration, host-side edge `org-red:backend → orchestrator`. Teardown = revoke keys.

**Runtime note (mesh-agent builder):** this fits the arena better than tenants did — `arena/run.sh` already boots one local mesh per instance, so org-per-scenario becomes N meshes on distinct ports, peered as the scenario dictates. Cross-org NPC initiation is **authorable**: an alias is stable author-chosen vocabulary (`rival-helpdesk:sam` can sit in persona text), and spin-up binds each alias to whichever mesh plays that role via an alias→mesh table; prompts stay byte-identical across runs and orgs.

## 12. Decisions (D) and owner questions (Q)

- **D1** Remote id `<alias>:<agent>`; new local ids may not contain `:`; legacy ones tolerated and logged.
- **D2** Two independent directional registrations, not a negotiated link (asymmetric states are legitimate; every status names its direction).
- **D3** Sender opens the socket; receiver authenticates with its own minted key; one socket per direction.
- **D4** `direct` only across borders in v1; kinds is a per-peering allowlist.
- **D5** Remote refusals reach the local sender as `REMOTE_REFUSED` (code only), best effort to a live socket, always recorded in `failed_code`.
- **D6** Receiver mints local row ids; dedupes on `(alias, remote_msg_id)`; peers get uniform `RELAY_REFUSED` for anything but rate limiting.
- **D7** Protocol version is checked at the WS handshake only, after the token resolves to a peer; absent = mismatch for peers, ignored for agents; `peers` stores no version.
- **D8** Local ack = accepted-and-queued (today's meaning); nothing defers it.
- **D9** F0 cherry-picks #84's mechanisms; #84 itself closes.
- **D10** A peer token has no expiry of its own; key expiry gates registration only; revocation is the kill.
- **D11** Second socket for the same peer alias: newer wins, older closed with `PEER_REPLACED`; `peerIndex` eviction is identity-guarded.
- **D12** Forwarder outcome taxonomy: `RELAY_REFUSED` permanent (fail + expire + `REMOTE_REFUSED`); `RATE_LIMITED`/`ACK_TIMEOUT`/`CONNECTION_RESET` transient (retry with backoff).
- **Q1 (owner):** direct-only across borders for v1 — confirm.
- **Q2 (owner):** peers reach each other over a trusted network (LAN/tunnel) for v1; public exposure stays with #74 — confirm.
